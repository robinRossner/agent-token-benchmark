# Task: task search endpoint

Add a search endpoint to the TaskFlow API: `GET /api/tasks/search`.

## Behaviour

Query parameters (camelCase, as everywhere in the API):

| Parameter | Required | Meaning |
| --- | --- | --- |
| `q` | yes | Search text. Trimmed; must be 1-100 characters after trimming. |
| `projectId` | no | Only search tasks of this project. An unknown project id simply yields an empty result. |
| `status` | no | One of `todo`, `in_progress`, `done`; anything else is a validation error. |
| `page`, `pageSize` | no | Standard pagination (default 1 / 20, max pageSize 100). |

Matching and ordering:

- A task matches when `q` occurs (case-insensitively, as a plain substring - not a regular expression) in its
  `title` or its `description`.
- Results are ordered with tasks whose **title** matches first, followed by tasks that only match in the
  description. Inside each of the two groups, order by `createdAt` ascending, then by id.
- The response uses the standard list envelope: `{ "data": [ ...tasks ], "meta": { "page", "pageSize", "total",
  "totalPages" } }`, where each item has the same shape as in `GET /api/tasks`.

Errors (standard error shape `{ "error": { "code", "message" } }`):

- Missing, empty or whitespace-only `q`, `q` longer than 100 characters, an invalid `status`, or invalid
  pagination values -> HTTP 400 with code `VALIDATION_ERROR`. For `q` problems the message must mention `q`.

The new route must not break `GET /api/tasks/:id` (e.g. `GET /api/tasks/t_1` still returns the task).

## Where things go

Follow `CONVENTIONS.md`: put the handler in `api/handlers/search.handler.js`, register the route in
`api/routes.js`, document it in `docs/API.md`, and add `test/search.handler.test.js`.

## Before you finish

Run `npm test` and `npm run lint`; both must pass.
