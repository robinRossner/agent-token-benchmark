# Task: task labels (8 steps)

Add **labels** to TaskFlow: per-project coloured tags that can be attached to tasks, filtered on, and shown in the UI.
Work through the steps below **in order**, finishing each step completely (code, and tests where stated) before
starting the next. **Every rule in `CONVENTIONS.md` applies to all code you write in every step** - naming, JSDoc,
logging, error and success response helpers, camelCase query parameters, ISO dates, `tf-` CSS classes,
`render<Name>` components, route registration plus docs, named exports, and tests. Re-check them as you go, not
just at the end.

## The 8 steps

**Step 1 - Data model.** A label is `{ id, projectId, name, color, createdAt }`. Ids are `l_1`, `l_2`, ... (the
first label created is `l_1`); `createdAt` is an ISO timestamp. The in-memory store keeps labels per project (no
seed labels). Every task gains a `labelIds` array of label ids, `[]` by default, including for all seeded tasks
and for tasks created later. Deleting a project also deletes its labels.

**Step 2 - Validation.** `name` is required, trimmed, 1-30 characters. `color` is optional, must look like
`#rrggbb` (hex digits, either case), and defaults to `#888888`. Label names are unique within a project,
compared case-insensitively. Invalid input -> `400 VALIDATION_ERROR`; a duplicate name -> `409 CONFLICT`.

**Step 3 - Label endpoints** (handler file `api/handlers/labels.handler.js`):

- `GET /api/projects/:id/labels` - list envelope (`{ data, meta }`), oldest first; `404 NOT_FOUND` for an unknown project.
- `POST /api/projects/:id/labels` - body `{ name, color? }`; returns `201` and `{ data: label }`.
- `PATCH /api/labels/:id` - partial update of `name` and/or `color` with the same validation (a label may keep its
  own name); `404 NOT_FOUND` for an unknown label.
- `DELETE /api/labels/:id` - returns `204`, removes the label and removes its id from every task's `labelIds`.

**Step 4 - Assigning labels to tasks.** `POST /api/tasks` and `PATCH /api/tasks/:id` accept `labelIds` (an array of
strings). Every id must be an existing label **of the task's own project**, otherwise `400 VALIDATION_ERROR`; a
value that is not an array is also a `VALIDATION_ERROR`. Duplicate ids in the array are collapsed. Task responses
include `labelIds`.

**Step 5 - Filtering.** `GET /api/tasks?labelId=l_1` (and `GET /api/projects/:id/tasks?labelId=...`) returns only
tasks whose `labelIds` contain that id; it combines with the existing filters and with pagination. An unknown
`labelId` returns an empty list (not an error).

**Step 6 - UI component.** Create `web/components/label-chip.js` exporting `renderLabelChip(label)`, returning
`<span class="tf-label-chip" data-label-id="l_1" style="background-color:#aabbcc">Name</span>`. The name is HTML-escaped;
if `label.color` is not a valid `#rrggbb` value use `#888888`. Add `.tf-label-chip` styles to `web/styles.css`.
Extend `renderTaskCard(task, options)` in `web/components/task-card.js`: when `options.labelsById` (an object
mapping label id to label) is given and the task has `labelIds`, render the chips of the labels that are found, in
the order of `task.labelIds`, inside `<div class="tf-task-card__labels">`. When there are none to show, do not render
that container.

**Step 7 - API client.** In `web/api-client.js` add `listLabels(projectId)` (GET `/api/projects/:id/labels`, returns
the `data` array) and `createLabel(projectId, { name, color })` (POST, returns the created label from `data`).

**Step 8 - Tests and docs.** Add `test/labels.handler.test.js` (API behaviour from steps 1-5, at least 8 tests) and a
web test file for the chip, the task-card labels and the client methods. Document every new endpoint in
`docs/API.md` (headings like `### GET /api/projects/:id/labels`), and describe the `labelIds` task field and the
`labelId` filter in the Tasks section of that file.

## Before you finish

Run `npm test` and `npm run lint`; both must pass.
